# 组会汇报：第二篇论文创新点探索与实验进展

> 日期：2026-09-01  
> 汇报主题：从 NCCL/RCCL 参数调优，收敛到“跨通信基座能力感知的端到端重叠策略选择”  
> 当前结论状态：**研究假设已有可复现实验入口，但论文创新尚未被端到端实验证实。**

---

## 0. 一分钟结论

我目前不建议把第二篇论文做成“为 RCCL 找一套更优的 algorithm/protocol/channel 参数”。四卡 NCCL/RCCL 的孤立 collective 实验显示，默认配置已经接近当前搜索空间中的较优值；继续做这类参数搜索，贡献会与 AutoCCL 高度重叠。

目前更有希望、且已出现第一批实证线索的方向是：

> 对有数据依赖的 AllGather-GEMM（简称 AG-GEMM），不能只用孤立通信带宽或完整 collective 完成时间选择策略。真正决定端到端时间的，还包括每个数据分片何时**合法可被 GEMM 读取**、GEMM 分块后的效率，以及通信和计算的资源竞争；这些边界会随着 NCCL/RCCL、NVSHMEM/DUSHMEM 等通信基座的能力和完成语义而变化。

截至目前，已经得到的事实是：

1. 在当前四卡基线中，NCCL 和 RCCL 的默认 collective 策略已经接近各自的孤立通信 oracle，单纯调参空间有限。
2. 海光侧已经用 DUSHMEM 的 on-stream `put + signal + wait` 构造并验证了正确的数据释放路径：14 个正式 case、数万 epoch、GPU 全 payload 校验均通过。
3. “发送方本地通信 stream 完成”与“接收方数据已经可被消费者合法读取”不是同一个时刻；本机测试中二者通常相差约 18--23 us。
4. DUSHMEM 的较优路径会随消息大小翻转：本机 4 KiB 下 `fcollect` 更好，而 1 MiB/64 MiB 下 `put-signal` 更好。

但目前**尚未**证明：DUSHMEM 已优于 RCCL、AG-GEMM 已获得加速、或“带宽最优与端到端最优不一致”已经发生。下一阶段必须在严格同构的 H0/D0/D1 对照中验证这些命题。

## 1. 研究问题如何收敛到当前方向

### 1.1 起点：为什么不直接做 AutoCCL 的跨平台版本

AutoCCL 的核心是对 collective 的底层执行参数进行自动调优，例如 algorithm、protocol、channel、线程资源和 chunk 等，并处理计算干扰。这个方向很重要，但若第二篇只是在 RCCL 上重复做同类搜索，主要问题有两个：

- **贡献重叠。**它仍然是“找更快的孤立 collective 配置”。
- **实证空间有限。**已有四卡扫描中，NCCL/RCCL 默认策略大多已接近扫描得到的较优结果，可能只有很小的边际收益。

因此，本工作不把 channel 或 protocol 当作论文的最终贡献，而把它们视为后续策略选择器的输入变量。

### 1.2 真正的问题：通信完成不等于数据可消费

AG-GEMM 中，通信先汇聚输入，GEMM 再消费这些输入。直觉上，若输入被切成若干 slice，某一 slice 到达后就可尽早计算对应 tile，通信和计算可能形成流水线。

但这里至少有五个不同的时间点，不能混为一谈：

```text
通信 API 返回
    != 发送方本地工作完成
    != 远端内存中似乎有数据
    != 远端数据对消费者可见且同步关系成立
    != 当前 slice 可被 GEMM 合法读取
    != 整个 collective 完成
```

所以，只测一个 isolated `busbw` 或完整 collective 的完成时间，未必能预测“最后一个 GEMM tile 什么时候结束”。这就是当前要验证的核心问题。

### 1.3 论文候选表述

当前工作标题可以暂定为：

```text
中文：面向异构 GPU 通信基座的完成语义与依赖释放感知
      Collective-GEMM 自适应重叠策略

英文：Beyond Bandwidth: Completion-Semantics-Aware Adaptive
      Collective-GEMM Overlap across GPU Communication Substrates
```

这里的“跨通信基座/跨平台”有严格含义：

- NVIDIA GPU 之间仍使用 NVIDIA 自己的通信栈，例如 NCCL/NVSHMEM；
- 海光 DCU 之间仍使用海光软件栈，例如 RCCL/DUSHMEM；
- **不会**把 NVIDIA GPU 和海光 DCU 放进同一个 collective group；
- 统一的是能力抽象、测量方法、候选策略表达和策略选择逻辑。

## 2. 先把实验对象和术语讲清楚

### 2.1 什么是 RCCL、DUSHMEM 和 AllGather-GEMM

| 名称 | 可以先这样理解 | 在本研究中的位置 |
|---|---|---|
| RCCL | 海光/ROCm 生态中的 GPU collective 通信库，与 NVIDIA 的 NCCL 承担类似角色 | 用 `AllGather` 建立标准、成熟的通信基线 |
| DUSHMEM | 面向 GPU 的 PGAS/单边通信库，支持设备侧 put、signal、wait、collective 等能力 | 用于显式构造“某个分片已可消费”的数据通路 |
| AllGather | 每个 rank 拥有一段本地输入；通信后每个 rank 都获得全部 rank 的输入 | AG-GEMM 中的通信算子 |
| GEMM | 矩阵乘法，是大模型中最常见、最主要的计算之一 | AG 后真正消费输入数据的计算算子 |
| slice / tile | slice 是通信数据的一个分片；tile 是使用该分片的一个 GEMM 子计算块 | 把通信依赖和计算依赖对齐的单位 |

在四卡 AllGather 中，每张卡最初只拥有自己的输入片段。AllGather 完成后，每张卡都拥有四张卡的完整输入。若第 `i` 个输入 slice 已被正确交付，理论上依赖它的 GEMM tile 可以提前开始，不必等所有 slice 都通信完成。

### 2.2 本工作最重要的时间定义

对某轮 AG-GEMM，从提交通信开始定义：

```text
t_issue                 通信任务被提交的时刻
t_release(i)            第 i 个 slice 首次满足依赖、可被对应 GEMM tile 合法读取的时刻
R_i = t_release(i) - t_issue
Delta_R_i = R_(i+1) - R_i
T_collective_done        所有通信数据都完成的时刻
T_done                   最后一个 GEMM tile 完成的端到端时刻
```

可用下面的时间线理解它们：

```text
t_issue
  |
  |---- slice 0 release ---- GEMM tile 0 ----|
  |               |---- slice 1 release ---- GEMM tile 1 ----|
  |                              |---- slice 2 release ---- GEMM tile 2 ----|
  |---------------------------------------------------- T_collective_done
  |-------------------------------------------------------------------- T_done
```

完整 collective 的 `T_collective_done` 只告诉我们“所有通信都结束了”；而对重叠而言，更关键的是第一片数据多久可消费（`R_0`）、相邻 slice 的释放间隔（`Delta_R_i`），以及计算是否能真正跟上释放速度。

### 2.3 H0、D0、D1 是什么

它们不是硬件代号，而是下一阶段用于公平比较的三种实验实现。

| ID | 做法 | 要回答的问题 |
|---|---|---|
| H0 | RCCL `AllGather` 全部完成后，再执行全部 GEMM | 标准 RCCL 串行基线 |
| D0 | DUSHMEM `fcollect` 全部完成后，再执行完全相同的 GEMM | DUSHMEM collective 的串行基线，排除“提前消费”因素 |
| D1 | DUSHMEM 用 `put-signal` 分 `q` 个 slice 传输；某 slice release 后立即执行对应 GEMM tile | 真正的 release-aware overlap 候选路径 |

后续可能增加 H1：RCCL 的合法分片/stream overlap 实现。但必须先清楚定义 RCCL 中何时允许消费某个分片，不能为了制造重叠而读取尚未得到正确同步保证的数据。

公平对比不是拿“整块 GEMM 的 H0”与“分块 GEMM 的 D1”直接比。D1 会因 tile 变小而损失 GEMM 效率，因此每个分块方案都必须有同样分块方式的串行对照。

## 4. 阶段 1：四卡 NCCL/RCCL 孤立 collective 基线

### 4.1 这组实验测了什么

在四张卡上使用 `nccl-tests` 或 `rccl-tests`，扫描 AllGather、AllReduce、ReduceScatter 等 collective；改变消息大小、algorithm、protocol、channel 等参数，记录正确性、带宽和日志。

NVIDIA 侧是四卡 RTX 4090/NCCL；海光侧原始结果和平台快照标识为：

```text
4 x K500SM_AI
gfx928:sramecc+:xnack-
PCIe
```

后续论文中应继续使用平台快照核验实际型号，不能把当前结果混写为 `K100_ai`、`K500SM_AI` 或其他架构代号。

### 4.2 可报告的基线数字

以下仅描述两台当前机器上的测量基线，**不是 NCCL 与 RCCL 软件质量的直接比较**。两侧的 GPU 型号、互联、NUMA、驱动、MPI 和通信库版本都不同。

| Collective / 消息大小 | 4 x RTX 4090 / NCCL busbw | 4 x K500SM_AI / RCCL busbw |
|---|---:|---:|
| AllGather 1 MiB | 8.357 GB/s | 6.441 GB/s |
| AllGather 64 MiB | 16.743 GB/s | 12.240 GB/s |
| AllReduce 64 MiB | 17.563 GB/s | 12.832 GB/s |
| ReduceScatter 64 MiB | 15.873 GB/s | 11.691 GB/s |

### 4.3 阶段 1 的可靠结论

1. **默认策略已经很强。**在当前扫描矩阵中，NCCL/RCCL 默认策略大多接近孤立通信较优值，说明仅靠搜索固定参数不容易构成强论文贡献。
2. **channel 不是跨平台常数。**RTX 4090/NCCL 的较大消息 Ring/Simple 通常在约 `ch4` 附近趋于饱和；当前海光 PCIe/RCCL 平台上，大消息常可从 `ch4` 到 `ch8` 继续获益。小消息下更多 channel 还可能更慢。
3. **路径选择与消息大小有关。**isolated 通信中某个协议的带宽较低，不足以推断它在 AG-GEMM overlap 中一定更差；因为 overlap 还会受 release、启动开销和资源竞争影响。

### 4.4 这组实验不能说明什么

- 不能说“4090 上 NCCL 比海光 RCCL 好”；这是不同机器的基线，不是控制变量下的库对照。
- 不能说“最优 channel 就是论文创新”；它只是候选策略的一维。
- 不能用 isolated `busbw` 直接推导 AG-GEMM 的端到端最优策略。

## 5. 阶段 2：旧 DUSHMEM 分块 AG-GEMM 探索的负结果

### 5.1 观察到的现象

先前海光侧的 DUSHMEM 分块 AG-GEMM 尝试中，`chunks = 2/4/8` 的端到端表现明显退化。同时，分块后的 GEMM 自身相对整块 GEMM 约有 `7.8--7.9x` 的性能退化。

### 5.2 这不是失败，而是排除了一个错误前提

这个结果说明：

```text
把通信切得更细
    不等于
通信和计算就会自动重叠得更好
    更不等于
端到端一定更快。
```

tile 太小会降低 GEMM 的算术强度、矩阵乘法 kernel 效率或调度效率；而新增的同步、通知、slice 管理开销也会增加。因此，重叠可能节省的等待时间，完全可能被分块计算损失吞掉。

### 5.3 这个负结果如何指导论文

它直接要求后续模型和实验同时考虑：

- `t_release(i)`：数据何时可合法消费；
- `q`：切成多少 slice；
- GEMM tile 形状与相同分块下的 GEMM 效率；
- 通信和 GEMM 同时运行时对 SM/CU、显存带宽和缓存的竞争。

它也规定了一个必要的实验规范：**D1 只能与相同 tile 划分的串行基线比较。**否则看到的“加速/退化”可能只是 GEMM 切块方式不同造成的假象。

## 6. 阶段 3：DUSHMEM Phase A 原语准入实验

### 6.1 这阶段刻意不测 AG-GEMM 加速

Phase A 只回答一个必要前提：在当前四卡海光环境中，能否用 DUSHMEM 构造一条**正确、稳定、可测量且具有明确 release 边界**的 AllGather 等价数据通路？

若这个前提不成立，后续“第 i 个 slice 到达后立即启动 GEMM”的实验没有可信基础。因此 Phase A 的目标不是证明 DUSHMEM 快，而是先证明它能被正确使用。

### 6.2 实验平台与通信路径

平台事实来自运行目录中的平台快照：

```text
GPU:              4 x K500SM_AI
reported arch:    gfx928:sramecc+:xnack-
topology:         全对全 PCIe；每个 GPU 对为 3 hops
DTK:              26.04
DUSHMEM:          3.2.5
HIP P2P:          所有异 rank 对均可达
dushmem_ptr:      所有异 rank 对均可用
```

核心路径是：

```text
发送端：dushmemx_putmem_signal_on_stream
接收端：dushmemx_signal_wait_until_on_stream
验证端：GPU 上对完整 payload 做 checksum / 内容校验
```

每个 rank 生成携带 `(producer_rank, epoch, word_index)` 信息的确定性 payload，并发送到其他三个 rank。接收端等待来自三个远端 rank 的单调 epoch signal，随后在 GPU 上校验四份数据。这个校验可以发现旧数据、写错 rank、写未完成或 buffer 被提前复用等错误。

为了安全复用环形 buffer slot，实验额外加入了单调 epoch + credit 协议：接收端只有在验证完数据后才回传对应 epoch 的 credit，发送端看到 credit 后才能复用 slot。这避免了简单 `ready=0/1` 标志可能引入的 ABA/buffer reuse 错误。

### 6.3 三个时间字段的意义

| 字段 | 直观解释 | 能否当作产品通信性能 |
|---|---|---|
| `issue_to_comm_stream_complete_us` | 发送方本地 communication stream 已完成所排队工作 | 只能说明本地工作完成，不能说明远端已可读 |
| `issue_to_release_us` | 接收方 wait stream 已看到所需 producer 的 epoch signal | 本实验中完整数据块的“合法消费”边界 |
| `issue_to_checked_us` | release 后还完成了 GPU 全 payload 校验 | 否；它包含故意加入的正确性验证成本 |

统计规则是：先在每个 epoch 对四个 rank 取最大值，再对所有 epoch 求 p50/p05/p95。这样报告的是四卡流水线整体的时间，而不是挑选最快 rank 的结果。

### 6.4 正式结果：14/14 case 全部通过

所有正式 case 均满足：MPI 退出码为 0、每个预期 epoch 有完整的四 rank 原始记录、GPU payload 全量校验通过。

| 路径 | Payload | Epoch 数 | p50 release (us) | p50 comm-stream (us) | p50 checked (us) | 状态 |
|---|---:|---:|---:|---:|---:|---|
| put-signal | 4 KiB | 10000 | 139.672 | 116.314 | 170.071 | PASS |
| put-signal | 64 KiB | 10000 | 151.512 | 131.673 | 196.469 | PASS |
| put-signal | 1 MiB | 10000 | 587.648 | 568.449 | 648.763 | PASS |
| put-signal | 8 MiB | 1000 | 3887.629 | 3866.510 | 4023.141 | PASS |
| put-signal | 64 MiB | 100 | 29937.010 | 29911.688 | 30905.249 | PASS |
| put-signal + quiet | 4 KiB | 10000 | 128.153 | 107.194 | 155.192 | PASS |
| put-signal + quiet | 1 MiB | 10000 | 588.448 | 569.728 | 646.205 | PASS |
| put-signal + quiet | 64 MiB | 100 | 29938.967 | 29914.885 | 30904.837 | PASS |
| credit, 1 slot | 4 KiB | 10000 | 138.072 | 115.834 | 167.190 | PASS |
| credit, 2 slots | 64 KiB | 10000 | 149.592 | 128.313 | 197.109 | PASS |
| credit, 4 slots | 1 MiB | 5000 | 569.089 | 550.690 | 616.686 | PASS |
| fcollect | 4 KiB | 10000 | 43.837 | 29.118 | 68.797 | PASS |

| fcollect | 64 MiB | 100 | 45923.909 | 45913.667 | 46888.533 | PASS |

### 6.5 观察一：本地完成与远端 release 确实不同

以 `put-signal` 为例，`release` 通常比 `comm-stream complete` 晚约 18--23 us；`fcollect` 中相应差距约为 10--15 us。

这不是要把这个差值解释成某个统一的网络 API 延迟。四卡的统计先进行了 max 聚合，它只是一个十分直接的实验事实：

```text
发送端本地通信工作完成
    不能替代
接收端数据已经满足消费依赖。
```

这正是后续必须显式测量 `t_release(i)` 的理由。

### 6.6 观察二：较优 DUSHMEM 路径随消息大小翻转

在相同负载和相同“数据可消费并通过验证”定义下，`checked` 时间的自动对照如下：

| 对照 | 4 KiB | 1 MiB | 64 MiB |
|---|---:|---:|---:|
| `put-signal + quiet` 相对 `put-signal` 的变化 | -8.749% | -0.394% | -0.001% |
| `fcollect` 相对 `put-signal` 的变化 | -59.548% | +25.598% | +51.717% |
| 当前较优路径 | `fcollect` | `put-signal` | `put-signal` |

这个现象只能在下面的边界内解释：当前机器、当前 DUSHMEM 版本、当前 on-stream API、当前正确性协议和当前消息大小。它支持“策略随能力和输入变化”的研究动机，但还不构成 AG-GEMM 加速证据。

### 6.7 Phase A 已经证明与尚未证明的内容

**已经证明：**

- 当前四卡海光平台上，`put-signal -> signal-wait` 可以作为后续分片 release 的正确候选原语；
- 单调 epoch + credit 可以安全复用 slot；
- 不同消息大小存在不同的较优 DUSHMEM 路径；
- release 是可定义、可记录、可在正确性条件下测量的事件。

**没有证明：**

- DUSHMEM 一定优于 RCCL；
- DUSHMEM 一定能提升 AG-GEMM；
- 当前不加 `quiet` 的结果可以泛化到所有 API、拓扑、驱动版本或通信模式；
- `checked` 时间可直接当作真实应用的通信性能。

## 7. 第二篇论文的候选创新点

### 7.1 待验证的中心假设

论文不应预设“DUSHMEM 替代 RCCL”，而应验证下列可证伪命题：

> 对于有数据依赖的 AG-GEMM，isolated collective 带宽最优或完整 `T_collective_done` 最小的策略，并不总是端到端 `T_done` 最小的策略。只有同时考虑分片的合法 release 曲线、GEMM 分块效率、通信-计算竞争以及通信基座可支持的策略集合，才能稳定选到接近最优的执行策略。

论文需要看到的关键现象是“排序反转”：

```text
策略 A：isolated busbw 最好
策略 B：完整 collective T_collective_done 最小
策略 C：AG-GEMM T_done 最小

若 A、B、C 在部分 workload 中不同，且原因可由 release/竞争/分块效率解释，
则问题本身成立。
```

### 7.2 为什么这个问题与已有工作有区别

| 对象 | 已覆盖的重点 | 本研究需要超出的部分 |
|---|---|---|
| 第一篇论文 | one-sided、ready 单元、细粒度依赖重叠、staging/window 等机制 | 不能只重做一个 chunk/ready/window 重叠机制；要强调跨基座能力与端到端策略选择 |
| AutoCCL | collective algorithm/protocol/channel/chunk 等低层调优与在线试探 | 不能只优化孤立 collective；要把合法 release 和 downstream GEMM 纳入目标 |
| 仅做 kernel fusion 的方案 | 通信与计算融合或并发 | 不能只声称“融合更快”；必须证明何时、为何、在何种基座能力下应该选择某条路径 |

### 7.3 候选能力向量与候选策略

不同平台不要求支持完全相同的 API；统一的是抽象字段。可先定义：

```text
B = {
  transport path,
  P2P availability,
  put/get capability,
  signal/wait cost,
  fence/quiet semantics and cost,
  supported collective paths,
  channel range,
  warp/wave granularity,
  GEMM throughput,
  memory bandwidth,
  communication-compute contention
}
```

每个候选策略写成：

```text
s = {
  backend/API,
  algorithm/protocol/channel (when supported),
  slice count q,
  slice size,
  GEMM tile shape,
  pipeline depth/window
}
```

例如，海光可比较 `RCCL AllGather`、`DUSHMEM fcollect`、`DUSHMEM put-signal`；NVIDIA 可在后续比较 `NCCL AllGather`、`NVSHMEM collective`、`NVSHMEM put-signal`。若某个平台不支持某策略，应明确记录为 capability mask，而不是强行伪造对等实现。

### 7.4 端到端代价模型的初步形式

目前不应宣称已经得到精确模型，可先把下面形式作为实验组织框架：

```text
T_e2e(s) = T_fill(B, s)
         + (q - 1) * II(B, s)
         + T_drain(B, s)

II(B, s) = max(T_comm_slice_and_release(B, s), T_gemm_tile(B, s))
         + T_contention(B, s)
```

其中：

- `T_fill` 是第一批 slice 和 tile 的启动开销；
- `II` 是流水线进入稳态后的相邻工作间隔；
- `T_drain` 是最后几片通信/计算排空的时间；
- `T_comm_slice_and_release` 不能只用发送端 API 返回或 busbw 代替；
- `T_contention` 表示通信和 GEMM 对 CU/SM、显存带宽、缓存等资源的影响。

如果后续数据不能支持这种结构，模型应被收缩或修改；模型必须服务于测量事实，而不能反过来解释一切。

## 8. 下一阶段 Phase B：决定主线是否成立的实验

### 8.1 实验目标

在严格相同的数学问题、数据布局、tile 数和正确性标准下，比较 H0、D0、D1，回答：

1. D1 是否相对其**相同分块方式的串行基线**有端到端收益？
2. isolated collective 的路径排序，是否会和 AG-GEMM `T_done` 排序不同？
3. 最优 slice 数、tile 形状与通信路径是否随消息规模/GEMM 强度改变？
4. 若有反转，能否用 release curve 与资源竞争解释，而不是偶然噪声？

### 8.2 第一轮正式矩阵

| 维度 | 第一轮取值 | 原因 |
|---|---|---|
| world size | 4 | 与已完成 RCCL/NCCL 基线一致 |
| AllGather 总数据量 | 4 MiB、16 MiB、64 MiB | 覆盖小/中/大通信区间 |
| slice 数 `q` | 1、2、4、8 | 包含无分片和逐步增加的管理开销 |
| GEMM 强度 | light、balanced、compute-heavy | 观察通信主导、平衡和计算主导场景 |
| 策略 | H0、D0、D1 | 先建立最小、可解释对照 |
| 预热 | 50 iterations | 排除首次分配、模块加载、时钟稳定过程 |
| 采样 | 小/中消息 500；64 MiB 100 | 在总实验时间内得到分位数统计 |
| 独立重复 | 每个 case 5 次独立进程 | 识别运行间波动，避免只报告单次偶然结果 |

可先用 `q=4` 做预筛：若已有明显且稳定的端到端排序反转，再完整扫描 `q=1/2/4/8`。若完全没有交叉趋势，则不应无限扩张参数矩阵，应先诊断 release 与 GEMM tile 效率。

### 8.3 每个 iteration 必须保存什么

每个 rank、每个 iteration、每个 slice 都应写入原始 CSV，至少包含：

```text
run_id, case_id, rank, iteration, slice_id,
t_issue,
t_release(slice_id),
t_gemm_start(slice_id),
t_gemm_end(slice_id),
T_collective_done,
T_done,
payload/tile correctness,
strategy parameters and platform metadata
```

每次运行还应保存：

```text
command.txt                  可精确重放的命令
stdout_stderr.log            完整标准输出与错误输出
platform/                    GPU、DTK/ROCm、MPI、拓扑、环境快照
raw/                         未聚合的每-rank CSV
analysis/                    p05/p50/p95、四 rank max、聚合比较表
manifest.csv                 case 参数、退出状态、结果目录
```

原则是：分析脚本只生成派生结果，绝不覆盖原始 CSV。失败 case 也必须留下命令、错误日志和 manifest 行，不能静默删除。

### 8.4 正确性要求

性能结果只有在以下条件全部满足时才进入统计：

1. MPI 进程退出码为 0；
2. 每个预期 rank/iteration/slice 都有完整记录；
3. GEMM 输出与对应串行参考结果在预设误差阈值内一致；
4. D1 中每个 GEMM tile 的开始时刻不早于其依赖 slice 的 `t_release(i)`；
5. 对 slot/window 的重用仍遵守 epoch + credit 或同等安全协议。

### 8.5 如何判定“创新假设成立”

至少要同时看到以下四类证据：

| 证据 | 合格现象 |
|---|---|
| 排序反转 | A 的 isolated 通信更快，但 B 的 AG-GEMM `T_done` 更短，且差异超过重复测量噪声 |
| release 解释 | B 有更早的 `R_0`、更小的 `Delta_R_i`，或更适合流水线的 release 曲线 |
| 分块公平性 | B 的收益不是因为与 A 使用了不同数学工作量或不同 tile 基线 |
| 可泛化性 | 至少在多个消息规模/GEMM 强度中出现可解释边界；再向 NVIDIA/NVSHMEM 做同抽象验证 |

可定义一个直观的收益量：

```text
E_0 = T_done(H0) - T_done(D1)
```

`E_0 > 0` 只说明 D1 相对标准 RCCL 串行 H0 更快；它还不足以排除“DUSHMEM 自身 collective 更快”或“分块基线不公平”。因此应同时报告 D0 和同分块串行基线。

### 8.6 什么结果意味着应收缩或放弃这个主线

负结果同样有价值。若稳定观察到以下任一情况，就不应继续把“release-aware selector”当作核心创新：

- 任意策略的 isolated 排序和端到端排序始终一致；
- release 差异相对于测量噪声或 GEMM 时间极小，无法影响 `T_done`；
- 分块 GEMM 的损失在全部形状下都远大于可能隐藏的通信时间；
- D1 的正确性或安全 slot 重用无法稳定满足；
- 策略最优性无法用少量能力/校准特征预测，只能靠穷举搜索。

这时应根据真实瓶颈改变问题，例如转向“分块 GEMM 效率约束下的 overlap 区间”或其他得到实证支持的方向，而不是强行包装一个选择器。

## 9. 当前结论的边界：组会上必须主动说明

### 可以明确说的

1. 四卡 NCCL/RCCL 的 isolated collective 基线已经充分说明：仅做 algorithm/protocol/channel 搜索的论文空间较小。
2. DUSHMEM 在本机确实拥有可用的 device/peer 通信与 on-stream 同步能力；不能把海光简单描述成“没有 device-initiated communication”。
3. Phase A 用强正确性校验建立了一个能够测量 `release` 的 DUSHMEM 通路。
4. 当前小/大消息的路径选择发生翻转，固定单一路径不是合理的默认假设。

### 不能提前说的

1. “DUSHMEM 比 RCCL 快。”目前没有同一 workload、同一 tile、同一正确性口径下的 H0/D0/D1 对照。
2. “RCCL 做不到的能力可以由 DUSHMEM 自动弥补。”DUSHMEM 提供更显式的 put/signal/wait 原语，但最终端到端收益必须实测。
3. “已经实现并证明了通信计算重叠加速。”Phase A 没有 GEMM 消费者，旧 chunk 实验反而显示分块会退化。
4. “这已经是论文创新。”目前只是一个有实验入口、可以被证伪的研究假设。

这种边界表述不是保守措辞，而是保证第二篇论文最终证据链可靠的必要条件。

## 附录 A：一句话解释常见疑问

| 疑问 | 回答 |
|---|---|
| 为什么不是直接把 DUSHMEM 塞进 RCCL？ | 还不知道真正瓶颈是否在 RCCL 内部。先做外部、可控且正确的 H0/D0/D1 对照，才能证明是否值得改库。 |
| 为什么 `put` 后还要 signal/wait？ | put 表示写入请求发出或本地工作推进；消费者需要一个与数据可见性、依赖关系匹配的同步点，才能合法读数据。 |
| 为什么要测 release，而不是只测通信时间？ | downstream GEMM 只能在数据满足依赖时启动。完整通信结束太晚，本地通信完成又可能太早，release 才是连接通信与计算的关键边界。 |
| 为什么分块后反而可能更慢？ | tile 变小会损失 GEMM 效率，并新增同步与调度开销；重叠节省的等待不一定抵得过这些成本。 |
| 这项工作最终的正结果可能是什么？ | 证明“孤立带宽/完整完成时间会选错 AG-GEMM 策略”，并用 release、tile 效率和能力特征选出接近端到端最优的策略。 |
| 如果没有排序反转呢？ | 应如实收缩或换题，不能把参数扫描包装为新机制。负结果会明确告诉我们该主线的适用边界。 |
