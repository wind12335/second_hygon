# 海光四卡实验执行说明

本文档对应 `run_4gpu_rccl_experiments.sh`。本文档固定针对当前本机海光平台：**4 张 K500SM_AI，gfx928，四卡均为 PCIe 互联**。目标是先建立可复现的 RCCL 四卡基线，再进入 DUSHMEM/AG–GEMM 重叠实验。所有结果都必须保留在一次运行生成的时间戳目录中，不覆盖旧结果。

## 0. 平台与版本原则

本轮不混入任何其他机器的配置或结果。当前本机已经实测确认：

```text
GPU model: K500SM_AI ×4
GPU arch: gfx928
interconnect: PCIe
```

本机平台快照命令为：

```bash
rocm-smi --showproductname --showtopotype
rocminfo
hipcc --version
```

本轮固定使用 `GPU_ARCH=gfx928`。如果将来换到其他机器，必须另建结果目录和单独的平台记录，不得覆盖本机四卡结果。

`/root/private_data/lyc/rccl-tests` 和 `/root/private_data/lyc/communication/rccl-tests` 是不同源码版本。建议使用前者重新编译；如果暂时使用后者已有 binary，必须在日志中记录其 git commit，并且不要与新编译结果混在同一运行目录。

## 1. 编译 RCCL tests

以下命令针对当前本机海光四卡执行，固定使用 `GPU_ARCH=gfx928`。

```bash
export RCCL_SRC=/root/private_data/lyc/rccl-tests
export HIP_HOME=/opt/dtk
export RCCL_HOME=/opt/dtk
export MPI_HOME=/opt/mpi
export GPU_ARCH=gfx928

cd "$RCCL_SRC"
make MPI=1 MPI_HOME="$MPI_HOME" HIP_HOME="$HIP_HOME" \
     NCCL_HOME="$RCCL_HOME" GPU_TARGETS="$GPU_ARCH" -j"$(nproc)"

ldd build/all_gather_perf | grep -E 'librccl|amdhip|mpi'
git log -1 --format='%H %ad %s' --date=iso
```

如果源码版本的 Makefile 不接受 `GPU_TARGETS`，可以去掉该变量，但必须检查编译产物确实包含 gfx928 目标。不要使用其他架构编译的旧 binary。

## 2. 创建一次不可覆盖的运行目录并保存平台快照

```bash
cd /root/private_data/lyc/2ndpaper

export GPU_MODEL=k500sm_ai
export GPU_ARCH=gfx928
export RCCL_TESTS_DIR=/root/private_data/lyc/rccl-tests
export RCCL_BUILD_DIR="$RCCL_TESTS_DIR/build"
export RESULT_ROOT=/root/private_data/lyc/2ndpaper/results
export GPU_VISIBLE=0,1,2,3
export RCCL_VERSION_TAG=rccl_$(date -u +%Y%m%d)

./run_4gpu_rccl_experiments.sh platform
```

输出目录类似：

```text
/root/private_data/lyc/2ndpaper/results/k500sm_ai_gfx928_4gpu/20260825T120000Z/
```

其中包含：

```text
platform/       平台、拓扑、版本、环境快照
logs/           每个 case 的完整 stdout/stderr 和退出状态
csv/            RCCL tests 导出的 CSV
commands/       每个 case 的可重放命令
manifest.tsv    所有 case 的索引、退出状态、日志路径和 CSV 路径
run.log         运行过程摘要
```

再次运行时不要手动复用旧 `RUN_ID`。默认时间戳会生成新目录；只有在明确需要重跑同一个实验时才设置 `RUN_ID`，并确认不会覆盖已有目录。

## 3. 四卡预检：先确认正确性，再跑性能

```bash
./run_4gpu_rccl_experiments.sh preflight
```

预检测试：

```text
AllGather、AllReduce、ReduceScatter
4 KiB、1 MiB、64 MiB
默认策略
warmup=10、iters=50、correctness=1
```

RCCL PCIe 平台统一设置：

```text
HSA_FORCE_FINE_GRAIN_PCIE=1
```

如果机器允许系统级设置，可以在实验前关闭 NUMA 自动均衡；如果没有权限，不要伪造结果，只把当前状态保存在 `platform/`：

```bash
sudo sysctl kernel.numa_balancing=0
```

预检中任何 `FAIL`、`TIMEOUT`、`ERROR` 或 `wrong_count != 0` 都必须先处理，不得进入后续矩阵。

## 4. 代表性四卡矩阵

```bash
./run_4gpu_rccl_experiments.sh representative
```

该阶段扫描：

```text
collective: AllGather、AllReduce、ReduceScatter
size: 4K、64K、1M、8M、64M、256M
config: DEFAULT、Ring/Simple、Ring/LL、Tree/Simple、Tree/LL
channels: DEFAULT
warmup=10、iters=50、check=1、average=max-rank
```

代表性、channel、full 和 mapping 阶段默认对每个配置执行 3 次独立运行（`CASE_REPEATS=3`）；预检阶段只执行 1 次。每次独立运行有不同的 case 名、日志和 CSV。若要增加重复次数，例如 5 次：

```bash
CASE_REPEATS=5 ./run_4gpu_rccl_experiments.sh representative
```

每个 case 都有独立的 `.log` 和 `.csv`。旧版本 rccl-tests 如果不支持 `-M/--output_algo_proto_channels`，脚本会自动跳过该选项；此时实际算法、协议和 channel 需要通过下面的 INFO 证据命令确认。

## 5. Channel 扫描

```bash
./run_4gpu_rccl_experiments.sh channels
```

该阶段在 `1M、8M、64M` 上扫描：

```text
Ring/Simple、Ring/LL、Tree/Simple、Tree/LL
channels = 1、2、4、8
```

如果四卡机器的 RCCL 实际 channel 范围更大，再追加 `16、32`，但先确认 INFO 日志显示请求值被实际接受。

## 6. 完整算法/协议矩阵

```bash
./run_4gpu_rccl_experiments.sh full
```

只有在预检和代表性矩阵稳定通过后才运行。该阶段不做 channel 的笛卡尔积，避免在没有研究证据之前消耗大量时间。`channels` 阶段单独承担 channel 扫描。

## 6.1 RCCL 细粒度 `duNcclAllgather` 探索（与标准 rccl-tests 分开）

`2ndpaper/rccl_smoke.cpp` 调用的是海光扩展的 `duNcclAllgather`，不是标准 `ncclAllGather`。它适合观察底层 `proto/algo/nChannels` 的可用性，但当前输出的带宽是自定义 algorithm-bandwidth 口径，不能直接与 RCCL tests 的 `busbw` 混图。换到四卡或换架构后必须重新编译：

```bash
cd /root/private_data/lyc/2ndpaper
export ARCH=gfx928
./build.sh

export SMOKE_OUT=/root/private_data/lyc/2ndpaper/results/duNccl_4gpu_$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p "$SMOKE_OUT"
env HIP_VISIBLE_DEVICES=0,1,2,3 \
    HSA_FORCE_FINE_GRAIN_PCIE=1 \
    NCCL_DEBUG=WARN \
    WARMUP=10 REPS=50 \
    mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
    ./rccl_smoke \
    > >(tee "$SMOKE_OUT/rccl_smoke.log") 2>&1
```

该日志必须单独标注 `api_variant=duNcclAllgather`。如果要和标准 RCCL tests 做严格比较，优先使用相同的 event 计时和统一 harness；不要把这里的 `GB/s` 数值直接当成 `busbw`。

## 7. INFO 证据：确认真实 transport、算法、协议和 channel

性能矩阵使用 `NCCL_DEBUG=WARN`，避免日志扰动计时。每个平台至少对每个 collective 运行一组代表性 INFO 证据，完整保存 stdout/stderr：

```bash
cd /root/private_data/lyc/2ndpaper
export INFO_OUT=/root/private_data/lyc/2ndpaper/results/info_$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p "$INFO_OUT"

env HIP_VISIBLE_DEVICES=0,1,2,3 \
    HSA_FORCE_FINE_GRAIN_PCIE=1 \
    NCCL_DEBUG=INFO \
    NCCL_DEBUG_SUBSYS=INIT,GRAPH,COLL,TUNING,TASK \
    mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
    /root/private_data/lyc/rccl-tests/build/all_gather_perf \
      -b 1M -e 64M -f 2 -g 1 -w 2 -n 5 -c 1 -a 3 -O 1 \
    > >(tee "$INFO_OUT/allgather.info.log") 2>&1

env HIP_VISIBLE_DEVICES=0,1,2,3 \
    HSA_FORCE_FINE_GRAIN_PCIE=1 \
    NCCL_DEBUG=INFO \
    NCCL_DEBUG_SUBSYS=INIT,GRAPH,COLL,TUNING,TASK \
    mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
    /root/private_data/lyc/rccl-tests/build/all_reduce_perf \
      -b 1M -e 64M -f 2 -g 1 -w 2 -n 5 -c 1 -a 3 -O 1 \
    > >(tee "$INFO_OUT/allreduce.info.log") 2>&1

env HIP_VISIBLE_DEVICES=0,1,2,3 \
    HSA_FORCE_FINE_GRAIN_PCIE=1 \
    NCCL_DEBUG=INFO \
    NCCL_DEBUG_SUBSYS=INIT,GRAPH,COLL,TUNING,TASK \
    mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
    /root/private_data/lyc/rccl-tests/build/reduce_scatter_perf \
      -b 1M -e 64M -f 2 -g 1 -w 2 -n 5 -c 1 -a 3 -O 1 \
    > >(tee "$INFO_OUT/reducescatter.info.log") 2>&1
```

不要把 INFO 日志作为性能平均值；它们只作为选路和真实配置证据。

## 9. DUSHMEM 原语实验：与 RCCL 基线分开保存

DUSHMEM 原语不能和 RCCL tests 的 CSV 混在同一文件。先确保现有二进制是按本机 gfx928 重新编译的。

```bash
cd /root/private_data/lyc/2ndpaper
export DUSHMEM_OUT=/root/private_data/lyc/2ndpaper/results/dushmem_4gpu_$(date -u +%Y%m%dT%H%M%SZ)
mkdir -p "$DUSHMEM_OUT"

env HIP_VISIBLE_DEVICES=0,1,2,3 HSA_FORCE_FINE_GRAIN_PCIE=1 \
  mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
  ./dushmem_probe \
  > >(tee "$DUSHMEM_OUT/dushmem_probe.log") 2>&1

env HIP_VISIBLE_DEVICES=0,1,2,3 HSA_FORCE_FINE_GRAIN_PCIE=1 \
  mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
  ./dushmem_sig_loop \
  > >(tee "$DUSHMEM_OUT/dushmem_sig_loop.log") 2>&1

env HIP_VISIBLE_DEVICES=0,1,2,3 HSA_FORCE_FINE_GRAIN_PCIE=1 \
  mpirun --allow-run-as-root -np 4 -mca coll ^hcoll \
  ./dushmem_sig_mono \
  > >(tee "$DUSHMEM_OUT/dushmem_sig_mono.log") 2>&1
```

这些实验需要分别记录：`put`、`get`、signal、wait、quiet、barrier 的正确性和耗时。不能把发送端函数返回直接称为远端数据到达。

## 10. AG–GEMM 重叠实验的最低要求

RCCL tests 只能给出整个 collective 的时间，不能得到每个 slice 的 `R_i`。后续 AG–GEMM harness 必须至少保存：

```text
T_comm
T_done
R_0 ... R_(q-1)
T_serial
T_overlap
T_e2e
GEMM-only time
GEMM slowdown under communication
correctness
```

实验顺序：

```text
S0: 完整 AllGather -> 完整 GEMM
S1: q=2/4/8 的 event 驱动 slice pipeline
S2: DEFAULT、Ring/Simple、Ring/LL、Tree/Simple、Tree/LL
S3: channel 与 q 的交叉点
S4: 通信-only、GEMM-only、串行、双 stream 重叠
```

每次运行仍然使用一个新的时间戳目录，不能只把最后一行平均值复制到总表。

## 11. 进入代价模型前的 go/no-go 判定

只有同时满足以下条件，才开始写跨基座能力感知的选择器：

1. 四卡至少有两种正确、稳定、可重复的候选策略；
2. 默认策略与 oracle 策略存在稳定差距；
3. `isolated bandwidth/T_done` 最优和 AG–GEMM `T_e2e` 最优出现排序反转；
4. `R_i` 或 release curve 能解释排序反转；
5. 现象在保留的 shape、slice 数或 rank mapping 上仍然成立。

如果只有 RCCL collective 带宽差异，而 `T_e2e` 排名始终一致，不要直接宣称已经验证了完成语义感知选择器。
