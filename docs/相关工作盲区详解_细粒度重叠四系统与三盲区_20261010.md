## 1. 术语先补齐(按出场顺序)

### 1.1 张量并行(TP)与 AllReduce:一步 decode 里到底发生了什么

张量并行 = 把一层网络的**权重矩阵竖着切成 16 份**,16 张卡各拿一份,各自算自己那份乘法。
问题:每份算出来都只是"部分和",必须把 16 张卡的部分和**加起来**才能得到正确结果——
这个"全体相加"的集合通信操作就叫 **AllReduce(AR)**,是 TP 的固有税。

Llama-3-70B 有 80 层,每层要交 2 次税(注意力一次、MLP 一次):
**80 层 × 2 = 每个 decode step 恰好 160 次 AllReduce**。
我们 trace 里实测 41,538 次 / ~260 step = 160.0 次/step,和理论严丝合缝。

我们窗口内一步 decode 的平均账单(30.3s ÷ 258 step ≈ 117ms/step;2026-10-10 修正口径,见 §1.5 与 ⑦ 号实测时间线):

| 项 | 每步平均 | 占比 |
|---|---|---|
| AllReduce kernel(名义) | ~80 ms | ~68%(busy 口径 85%) |
| 其中:走线+协议(全局最小时长) | ~15 ms | **~13%** |
| 其中:**kernel 内等待** | ~65 ms | **~55%** |
| 全部计算(GEMM+注意力+杂项) | ~18 ms | ~15% |
| GPU 空闲(kernel 间隙) | ~18 ms | ~15% |

(四项合计与 117ms 的出入来自取整与少量杂项 kernel;口径见 REPORT.md §④ 修正)

### 1.2 prefill / decode / M

- **prefill(预填充)**:请求刚进来,把整个 prompt(几百~几千 token)一次算完。
  一次 GEMM 的 M 维(token 数)很大,计算量大,卡是饱的。
- **decode(解码)**:之后每生成一个 token,就把"整个 batch 里所有请求各 1 个 token"再过一遍全网。
  **M = 这一步参与计算的 token 总数**。我们负载 conc=16(16 个请求并发)→ M≈32。
- 我们采集的窗口 decode 为主导 → **M≈32,一个典型的"小 M"场景**。

### 1.3 锁步(lockstep)

锁步 = 16 个 rank(进程)执行**完全相同的程序序列**,像阅兵方阵一样每一步都对齐。
TP 天然如此:所有 rank 跑同一个模型、同样的层顺序。
证据:16 个 rank 的 AllReduce 计数**一字不差都是 41,538**。

锁步有个推论:任何一个 rank 在任何一处慢了,所有人从下一个 AllReduce 起一起慢——
**但"慢多少"不会体现在 kernel 数量上,而是藏在 AR kernel 的时长里**(见 1.5)。

### 1.4 到达偏斜(arrival skew)与 straggler

16 个 rank 虽然程序相同,但每个 rank 到达同一个 AllReduce 的**时刻不同**
(CPU 派发 kernel 的抖动、操作系统调度、前序 kernel 快慢……)。这个时刻差叫**到达偏斜**。

- 习惯性迟到的 rank 叫 **straggler(慢者)**。我们实测它是**固定且轮换的**:
  **75% 的 AR 里全局最后到者在 worker-0**,pid931 独占 29.1%(pid927 12.9%、pid936 12.4%);
  worker-1 侧最常迟到的是 pid832(10.2%)。
- 偏斜还有**结构**(2026-10-10 修正,方向与初版报告相反):worker-1 的 8 个 rank
  **整队到达**(节点内到达散布中位仅 4µs);worker-0 内部散布中位 295µs——
  **大家在每个 AR 里等的是 head 节点上一两个迟到者**。head 同时跑着 vLLM 调度器/API
  进程,CPU 抢占是候选机制(待单机 hipprof/E1 验证)。

### 1.5 wire(走线)与 wait(等待):AR kernel 的时长怎么拆

关键事实:**RCCL 的集合通信 kernel 内部自带一个隐式同步点**。
kernel 开跑后并不立刻搬数据,而是先原地**自旋等待**(spin,反复轮询标志位)直到所有参与方的数据到齐,
到齐之后才真正搬运。所以每个 rank 上 AR kernel 的时长是两段:

```
dur(rank r) = 等待(等其他 rank 到齐,各 rank 不同) + 走线+协议(搬运+握手,基本相同)
```

怎么把两段分开测?**同一节点 8 个 rank 共享主机时钟**,把 41,538 个 AR 按序号对齐:

- `dur_min`(8 个 rank 里最短的那个)= 最后到达者自己的时长 ≈ **纯走线+协议**(它没等任何人);
- `dur_r − dur_min` = rank r 比"最晚者"早到的时间 = **它的 kernel 内等待**。

这就是 REPORT 里"AR 名义占墙钟 ~68–75%,其中约 4/5 是等待不是搬运"的来历。
一个内部自洽校验:逐 AR **全局**最小时长均值 ≈ 92µs × 161 次/步 ≈ 14.8ms/步,
与 3.82s ÷ 258 step 完全吻合。**注意 dur_min 必须取全局 16 rank 的最小值**:
若只取节点内最小,worker-1 的"最小时长"(均值 437µs)大头其实是在等 worker-0
的迟到者,会把等待误记成走线——初版 REPORT 即犯此错(26%/45%),修正后为 13%/55%。

**词源,以及"侧"是什么意思**:wire 直译"导线/走线"——网络行话 *data on the wire*
指"数据已上网线、正在路上"。节点内走片间互联的物理通路,节点间走 shca 400G 光纤;
wire ≈ 消息 ÷ 有效带宽 + 协议握手等固定开销(所以 512KB 的小消息 wire 也有 ~193µs,
纯载荷只占几十 µs,其余是树形协议逐跳与标志位轮询)。wait 则是"人在 kernel 里等人齐"的自旋。
所谓 **wire 侧 / wait 侧**,是把"通信占墙钟 ~75%"拆成的**两条互相独立的优化轴**("侧"=侧翼):

- **wire 侧**(本文窗口 ≈26% 墙钟)= 搬运时间:已有系统**全部**在这条轴上,
  手段是把搬运**藏**进计算缝隙(wire-hiding/藏走线,§1.6);
- **wait 侧**(≈45%)= 等人时间:重叠**藏不掉**(对端数据没到齐之前搬无可搬),
  只能靠调度消——本论文站这条轴。

后文一切"wire 侧收益 / wait 侧收益",读法都是"沿这条轴最多能省的墙钟"。

### 1.6 overlap(重叠)与 wire-hiding(藏走线);上限为什么是 min(通信, 计算)

- **overlap/重叠**:让通信和计算**同时**发生在不同流/不同资源上,而不是排队串行。
  我们 trace 的实测:**重叠 = 0.000s(16/16 rank)**——eager TP 下完全串行,这就是最原始的基线。
- **wire-hiding(藏走线)**:整个"细粒度重叠"谱系(四系统 + AsyncTP/TokenWeave)做的事——
  把通信拆碎、混进计算的缝隙里,让**走线那部分时间**被计算遮住。

上限可以用一个生活类比推出来:洗衣服(计算)40 分钟,烧水(通信)20 分钟。
同时开动,总耗时 = max(40, 20) = 40 分钟,**省下的是 min(40, 20) = 20 分钟**——
省的量永远不超过两者中较短的那个,因为 you can't hide more communication than there is
computation to hide it under(没有足够的计算来遮,遮不住的部分照样排在关键路径上)。

### 1.7 chunk(分块)、tile、mini-barrier、launch 开销、tile 量化损失

- **chunk/分块**:把一次大 AllReduce 拆成 k 次小 AllReduce,和计算交错执行(Flux 的做法)。
- **mini-barrier(小栅栏)**:barrier(栅栏)= 所有参与方到齐才放行的同步点。
  集合通信本身就是"分布式 barrier + 搬数据"。**拆成 k 块 = k 个小 barrier**,
  每个小 barrier 都要"人到齐"才走 → 每一块都会重新暴露一次到达偏斜(§3 的核心)。
- **launch 开销**:每个 kernel 从 CPU 派发到 GPU 开跑有固定成本(~5–20µs,eager 下更贵)。
  拆得越细,kernel 数越多,固定开销占比越高。
- **tile/量化损失**:GEMM 不是整块算的,按固定大小的 tile(如 64×16×128)切块。
  我们 trace 里的 kernel 名 `Cijk_Ailk_Bljk_..._MT64x16x128` 直接写着 tile 的 M 方向是 64——
  而 decode 时 M≈32,**连一个 tile 都填不满,一半算力在空转**。
  Flux 式"把 GEMM 也拆碎"会让每个碎块的 M 更小、浪费更多;
  FlashOverlap 的动机正是这个:**GEMM 不拆,一个 kernel 里边算边发信号触发通信**。

### 1.8 latency-bound / bandwidth-bound(时延主导 / 带宽主导)

- 消息大(如 prefill 的 256MB):时间 ≈ 字节数 ÷ 带宽,**带宽主导**。
- 消息小(如 decode 的 ~0.5MB):时间 ≈ 固定地板(协议握手、标志轮询、launch)+ **等待**,
  和消息大小几乎无关,**时延主导**。
- 关键:**等待部分 δ 由 rank 侧调度抖动决定,和消息大小完全无关**——
  消息缩 256 倍,δ 一分不少。这是 §5 "M 变小 → 通信占比暴涨"的机制。

### 1.9 eager 模式(我们的运行形态)

正常 PyTorch 每个算子单独派发 kernel,叫 **eager(逐算子)模式**;
更快的形态是先把整段计算编译/录制成"kernel 图"(CUDA Graph / dynamo 编译),一次启动。
我们环境里 DTK 的 dynamo 编译不了 vLLM(`--enforce-eager` 强制逐算子),
所以 16 rank 全程 eager:**重叠 = 0** 有架构原因,launch 开销也更大(那 15% 空闲的主要来源)。

## 3. 盲区一:四系统都假设"锁步到达",没有到达偏斜模型

### 3.1 他们考虑了什么、没考虑什么

四篇的公共前提:**集合通信的时长 ≈ 走线时间,各 rank 同时到达**。
在这个前提下,把通信拆碎混进计算,收益就是干净的"通信时间 × 重叠比例"。
公开论文/仓库中均没有对到达偏斜的测量、建模或注入实验;评测环境是均衡配置的
NVLink 单机/多机,负载同步启动,偏斜天然小,所以这个假设在他们的机器上**近似成立,
也就从未被检验**。

### 3.2 机制:细粒度化为什么可能"放大"等待

把一次 AR 拆成 k 块,k 个 mini-barrier 排成流水。每个 barrier 的规则不变:**到齐才走**。
于是每个 rank 的"早到优势"或"迟到劣势"在每个 barrier 处重新结算一次:

- **持续性慢模型**(straggler 每个 chunk 都慢一点,例如它的 CPU 派发持续抖):
  每个 mini-barrier 付一次到达差 → 总等待 ≈ k × δ,同时 protocol 地板也要付 k 次。
- **一次性迟到模型**(straggler 只在 step 开头迟到一次):
  第一个 barrier 吸收掉 δ,后面的 barrier 只继承逐次独立的抖动 σ → 总等待 ≈ δ + k×σ 量级,
  不放大但也不消失,且 k 次 launch+协议开销是确定的新增成本。

**两个模型的差别本身就是一个可测量的问题**,而我们手里有别人没有的数据:
16 个 rank × 41,538 个 AR 的逐集合 `(ts, dur)` 序列(已落盘在 `analysis/rank_*.json`)。

### 3.3 我们能做的模拟实验(数据在手,零新采集)

**E1: k-分块等待放大曲线**
1. 从对齐序列里取出每个 AR 的 8-rank 到达差 δ_i(共 41,538 个样本,含自相关信息);
2. 用经验分布模拟"每次 AR 拆 k 块"后每个 mini-barrier 的到达差
   (变体 a:沿用同一样本 δ_i = 持续性慢;变体 b:重采样 = 独立抖动);
3. 输出:总自旋等待 + k×launch/协议地板 随 k 的曲线,以及"分块开始亏本"的交叉点。

结论形态:在高偏斜环境(我们的 wait=45%),细粒度化的真实收益 =
理论重叠收益 − 放大的等待 − k 倍固定开销。**四篇论文的收益数字都是在低偏斜环境测的**,
这篇模拟给出它们在高偏斜环境下的修正系数。可选加分项:用 phase5 微基准注入可控偏斜实测验证。

## 4. 盲区二:只动 wire、不动 wait——天花板逐步推

### 4.1 一步一步算

记一步墙钟 T = 计算 C + 走线 W + 等待 Δ + 空闲 I,当前完全串行(重叠=0)。
任何 wire-hiding 方案的本质:**把 W 从关键路径上挪走,挪到 C 执行期间并发跑**。

- 并发段耗时 = max(被遮的 W, 遮它的 C)。按 1.6 的类比,**能省的上限 = min(W, C)**:
  没有足够的计算来遮时,遮不住的 W 照样排队。
- 代入 §2(修正口径):**min(3.8, 4.6) = 3.8s → wire 侧最多省 12.6% 墙钟**(30.3→26.5s,1.14×)。
- 最慷慨口径:W < C,遮蔽物充足而短板是 W 本身,连"拿空闲垫"也省不出更多:
  天花板仍是 **1.14×**——修正后 wire 侧比原先算的更窄。
- **注意整个推导里 Δ(13.8s)碰都没碰**:rank 到齐之前,通信 kernel 里该自旋还是自旋;
  把通信拆碎只是把自旋切碎(§3),不会消灭它。

### 4.2 wait 侧的池子没人认领

- wait 池 = **16.8s = 55% 墙钟**,是 wire 侧全部可省总量(3.8s)的 **4.4 倍**;
- 哪怕只回收一半(8.4s ≈ 28%),已是 wire 侧天花板的 2 倍多;理想全回收 = **2.24×**;
- 而且两条轴**正交、可叠加**:fusion 谱系负责把走线藏进计算,我们负责用到达结构消等待
  (例如让早到的 rank 先做不依赖对端的工作、按节点早晚重排任务)。互不竞争。

一句话:**在 M≈32 的 decode 里,"藏走线"是在追那 26%,"消等待"是在追那 45%;
前者的可省份额甚至被计算量(15%)卡得更死。**

### 4.3 为什么四篇没发现这个问题

它们的评测里 AR 时长 ≈ 走线(环境均衡,偏斜小),kernel 时长工具(Nsight 等)也不区分
kernel 内"等待"与"搬运"。分解 wait/wire 需要**同节点多 rank 按集合对齐**这种测法
(我们的 phase4 微基准 + phase6 框架级 trace 两层证据),这在它们的工具链里不存在。
TCP→IB 对照进一步加强因果:传输换了、跨节点到达改善 ~110× 之后**偏斜依旧**,
说明 wait 是计算/调度侧的产物,不是网络慢——换网解决不了,只有调度能解决。

### 4.4 组合的顺序:wait 侧是 wire 侧的前置条件(2026-10-10 增补)

wire+wait 兼得是终局,但顺序有讲究:§3.2 已论证 chunk 化把 wait 付 k 次——
**在高偏斜环境,fusion 谱系要先消 wait 才藏得动线**。wait 侧不是与 wire 侧并列的
第五个优化,而是它们的**使能器**。四级梯子(上界口径,论文须标注):

| 方案 | 时间线 | 剩余墙钟 | 加速比上界 |
|---|---|---|---|
| 现状(实测) | C+Δ+W+I 全串行 | 30.3s | 1× |
| 只做 wire 侧(完美藏线) | C+Δ+max(0,W−C)+I | ~87% | 1.14× |
| 只做 wait 侧(全消) | C+W+I | ~45% | 2.24× |
| **兼得(wait+wire)** | max(C,W)+I | ~30% | 3.3× |
| 理论完美(空闲也吸收) | max(C,W) | ~15% | 6.6× |

单做 wire 侧被 Δ 压死在 1.14×;单做 wait 侧(2.24×)已近其天花板的 2 倍。
实现路径:**P0**(本论文)eager 框架级 wait 调度 → **P1** 双流 AR∥独立算子(框架级)
→ **P2** chunk 化 RS+AG 重叠(依赖 Triton-DCU 路线验证),P2 的前置恰是 P0。

**wait 侧的现有最近邻(2026-10-10 复核)**:StragglAR(arXiv 2025-05,等待期非 straggler
先做 partial RS,straggler 到后新算法补完——把 wait 换成 wire)与同族 Efficient AllReduce
with Stragglers(2025-09);均为**算法级 + 单一已知 straggler**假设,微基准/仿真评测。
表达不了"半个节点整队晚到 + 每节点一个固定慢者"的实测结构,也无框架级 eager 实施、
无小 M decode、无 wait/wire 对齐分解测法。机制上它 wait→wire、我们 wait→compute/消除,
可叠加。训练系 async(SSP/Hogwild/backup workers)用陈旧梯度绕开等待,改语义,不适用 TP 推理。

## 5. 盲区三:M≈32 的 decode 是空白地带

### 5.1 M 变小时发生了什么(算术)

- GEMM 时间 ≈ ∝ M(tile 饱和区):M 从 8192 → 32,理论降 256×,叠加 tile 地板(MT64 填不满)
  实际降 ~2 个数量级 → 每步计算塌到 ~18ms;
- AR 消息也 ∝ M(约 256MB → ~0.5MB),**但** AR 时间 = 协议地板 + 载荷/带宽 + 等待 δ,
  后两项与 M 基本无关(M≈32 时纯载荷只有 ~10–20µs 量级,δ 照付 ~300µs)→
  AR 每次只降不到一个数量级;
- 一除:**comm/compute 从 phase5 微基准 M=8192 的 37%:63% ≈ 0.6×,涨到本窗口的 10.1×**。
  这条"M 曲线"就是我们两个实验(P5 微基准、P6 框架级)拼出来的分界证据。

### 5.2 为什么"藏走线"在小 M 天然失效

藏走线需要**足够多的计算**当遮蔽物。M≈32 时全部计算只有 15% 墙钟,
而要遮的走线+等待有 ~68%——遮蔽物严重不足(§4 的 min() 直接卡死)。
这不是工程优化能弥补的,是该方法在小 M 下的**结构性失效**。

## §9 全景:一条请求的一生

```
用户 ──HTTP──► API 进程(OpenAI 格式)
                 │  入队
                 ▼
            调度器 Scheduler(vLLM 引擎核心进程,在 worker-0 上)
                 │  每"一步"(step)动态拼一个 batch:哪些请求做 prefill、哪些做 decode
                 ▼
   驱动 rank(准备输入 token id、位置信息,广播给其余 15 个 rank,量极小)
                 │
   ┌─────────────┴──────────────────────────────┐
   │ 16 个 rank 各自前向(同一份程序,锁步执行) │  ◄── GPU 计算 + RCCL 通信全在这
   └─────────────┬──────────────────────────────┘
                 ▼
   lm_head 出 logits → 采样(temperature / top-p)→ 得到 1 个新 token
                 │
        token 追加到对应请求的序列,KV 已在层内缓存
                 ▼
        流式返回给用户;请求攒够 maxtok 或出 EOS 则离场,新请求补位
```

两个描述"用户体感"的指标:

- **TTFT**(Time To First Token,首 token 延迟)≈ 排队 + 该请求的 prefill 步;
- **ITPT**(Inter-Token Per Token,逐 token 间隔)≈ 每个 decode 步的耗时。
  我们窗口实测:**~117ms/step**(30.3s ÷ 258 个前向步)——这就是用户打字机间隔的来源。

关键角色说明:**rank** = 参与张量并行的一个 GPU 进程(本例 16 个,rank0–7 在 worker-0、
rank8–15 在 worker-1);**驱动 rank** = rank0,负责收输入、发结果。

## §10 预处理与 Embedding(第 161 次 AllReduce 就藏在这)

**分词(tokenization)**:文本先被**分词器**(Llama-3 用 BPE,Byte Pair Encoding——
把高频字节对逐步合并成子词的算法,词表共 128,256 个**词元 token**)切成整数 id 序列。
"我爱海光" → 形如 `[30219, 54233, 104039, 100158]` 的 id 数组(示意)。

**Embedding(嵌入)**:模型把每个 id 变成一个 8192 维向量。实现上就是**查表**:
一张 `128256 行 × 8192 列` 的大矩阵(参数量 10.5 亿),第 i 行就是词元 i 的"含义向量"。

**TP16 下怎么查**:16 张卡没人放得下也不需要整张表——**每 rank 只存 1/16 的行**(8016 行)。
查表时,落在自己区间内的 id 正常查,区间外的置零;然后一次 **AllReduce 求和**,
16 份"各自查了一部分"的结果加起来 = 完整的 `[M, 8192]` 输入(M = 本步 token 数)。

> **对账修正(本次自查发现)**:REPORT 原写"160 AR/step × ~260 step"。更精确的读数是
> **41,538 = 258 step × 161 AR/step**,其中 161 = 80 层 × 2 + **1(embedding 求和)**;
> 而窗口内 AllGather 恰好 258 次 = lm_head 每个前向步 1 次(见 §11 末尾)。整数严丝合缝,
> 且与 vLLM 的实现(词表并行 embedding 要 AR、logits 要 AG)一一对应。

## §11 一层 Transformer 的解剖:11 步走完一遍(单 rank 视角)

Llama-3-70B 配置(来自模型 config,全部可查):80 层,hidden=8192,注意力 64 个 Q 头 /
8 个 KV 头(GQA),每头维 128,MLP 中间维 28672,词表 128256,位置编码 RoPE,归一化 RMSNorm。
总参数 ≈70.6B(bf16 权重 141.1GB,每 rank 分到 8.8GB——与实测文件大小一致)。

TP16 切分:**Q 头每 rank 4 个;KV 头 8 个不够 16 分 → 每 rank 1 个、复制 2 份**;
MLP 中间维每 rank 1792;词表每 rank 8016 行。下面每步都标了**本仓 trace 里的真实 kernel 名**:

| # | 操作 | 在做什么(直觉) | TP16 下形状(单 rank) | trace 里的 kernel |
|---|---|---|---|---|
| 1 | 残差相加 + RMSNorm | 把上一层输出加回主干(残差=留后路),再做归一化:每个向量除以自己的均方根,让数值稳定。RMSNorm 比 LayerNorm 少一步减均值,更快 | `[M,8192]` 逐元素 | `fused_add_rms_kernel_opt` |
| 2 | QKV 投影(GEMM) | 一次矩阵乘同时算出本 rank 4 个 Q 头、1 个 K 头、1 个 V 头的向量。"投影"=乘一个可学习矩阵做线性变换 | `[M,8192]×[8192,768]`(4×128+128+128) | `Cijk_Ailk_Bljk_*`(hipBLASLt) |
| 3 | RoPE 旋转位置编码 | 把每个 token 的 Q/K 向量按其位置角度"旋转",使内积自带相对位置关系,无需显式位置参数 | 逐元素三角函数 | `rotary_embedding_kernel` |
| 4 | 写 KV cache | 把本步的 K/V 追加进显存缓存,之后不必重算历史 | 每层每 token 增 2×8×128×2B=**512B**,80 层共 **320KB/token** | cache 写入 kernel |
| 5 | 注意力(paged) | 每个 Q 对全部历史 K 打分(点积)→softmax 成权重→加权求和 V。decode 时每 token 只对历史扫一遍 O(L);prefill 是 M×M 两两打分 **O(M²)** | `[M,4头]×[L历史]` | `paged_attention_kernel` |
| 6 | 输出投影 o_proj(GEMM) | 把 4 个头的输出拼起来投影回 8192 维——但**只是 4/64 头的部分和** | `[M,512]×[512,8192]` | `Cijk_*` |
| 7 | **AllReduce ①** | 16 个 rank 的部分和相加 → 完整 `[M,8192]`。消息 = M×8192×2B(M=32 时 **512KB**) | 全 16 rank | `ncclDevKernel_AllReduce_Tree_LL_Sum_b16` |
| 8 | 残差 + RMSNorm(第二次) | 同 #1 | `[M,8192]` | `fused_add_rms_kernel_opt` |
| 9 | gate/up 投影(GEMM,融合) | MLP 第一层做成两份并行投影 gate 和 up(合一个 kernel),为 SwiGLU 做准备 | `[M,8192]×[8192,3584]`(2×1792) | `Cijk_*` |
| 10 | SiLU×up 激活 | SwiGLU:门控支路过 SiLU(x)=x·sigmoid(x) 后逐元素乘 up 支路——"软开关"决定信息通过多少 | `[M,1792]` 逐元素 | `act_and_mul_kernel_opt1` |
| 11 | down 投影(GEMM)+ **AllReduce ②** | 投影回 8192 维,又只是部分和 → 第二次 AR。MLP 每 rank 只见过 1792/28672 的中间维 | `[M,1792]×[1792,8192]` → AR | `Cijk_*` + 同上 AR |

80 层跑完 → 最终 RMSNorm → **lm_head**(`[M,8192]×[8192,8016]`,词表并行)→
**AllGather** 拼 16 段 logits 成 `[M,128256]` → 采样。logits = 每个词元的"得分";
采样按 softmax 概率抽(受 temperature 平滑、top-p 截断控制,本文负载取默认)。

**8.7ms/step**(平均 27µs/个——M=32 连一个 64 行的 tile 都填不满,kernel 名里
`MT64x16x128` 的 64 就是 tile 的 M 方向);AR = **161 个**,总 ≈ 87.6ms/step。

## §12 Prefill vs Decode:同一份代码,两种负载

| | **prefill(整段 prompt 一次算)** | **decode(每步每请求 1 token)** |
|---|---|---|
| M | 整段 prompt(几百~8000;超长会切成块,chunked prefill) | ≈ 并发请求数(本例 ~16-32) |
| GEMM | 大而饱满,tile 填满,卡算得动 | M=32,tile 利用率≤50%,每个仅 ~27µs |
| AR 消息 | M=8000 时 **131MB**(带宽主导) | M=32 时 **512KB**(时延+等待主导) |
| 注意力 | O(M²) 全两两打分,是大头 | O(L) 顺扫 KV cache,很小 |
| 用户体感 | 决定 **TTFT** | 决定 **ITPT**(打字机速度) |

**continuous batching(连续拼批)**:调度器每步重新拼 batch——刚到的请求进 prefill 组,
老请求各出 1 token 进 decode 组,做完的立刻离场、新请求补位。本例 conc=16、每请求 ≤128 token,
窗口以 decode 为主,平均 M≈32。

**M 曲线(我们的两个实验拼出的证据)**:phase5 微基准 M=8192 时通信占 37%;
本窗口 M≈32 时 85%。机制(§5.1):GEMM 时间 ∝ M 塌缩两个数量级,而 AR 时间有
"协议+等待"地板与 M 无关 → 通信占比暴涨。**M 是这条故事线的横轴。**

### §12.1 常见疑问(看 `03_prefill_vs_decode.html` 时)

- **Q:prompt 怎么会"并发"?一句话还能切开算?**
  A:并发的是**多个请求**(图中一行 = 一个用户的完整 prompt),不是把一句话拆给多人。
  GPU 一步 forward 的 batch 维 M 是拼出来的:稳态 decode 步 M = 活跃请求数(每请求 1 token)。
  单条 prompt 确实可能被切(chunked prefill),但那是**同一条 prompt 分几步算**:
  chunk2 的注意力经 KV cache 读到 chunk1 的 K/V,与一口气算完数学等价,生成内容连贯不变,
  只是首 token(TTFT)略晚。
- **Q:为什么 decode 有稀疏区和密集纯 decode 区?**
  A:稀疏段 = 爬坡期,新请求陆续 prefill,每步背着 prefill 块 → 步长 ~3× 且解码者少;
  密集段 = 稳态,全员 prefill 完毕,每步纯 decode、步长恒 117ms、所有行同时各出 1 token(锁步)。
  decode 间隔被拉长处 = 该步混有 prefill,这正是 Sarathi-Serve 用 chunked prefill 平滑的对象。
- **Q:每请求生成 64 = 64 次 decode?**
  A:对该请求是(参加 64 个 decode 步、每步 1 token);对墙钟不是 64×N——
  N 个请求拼进**同一个 batch** 一步算完(M=N,一步出 N 个 token)。
- **Q:并发会让通信开销大幅上升吗?**
  A:不会——**按 token 摊销反而大降**。每步 AR 次数固定 161(与并发无关);
  消息∝M 但小消息被协议地板罩着、等待与 M 无关 → conc 1→16:每步 AR 时间仅 ~70→~88ms,
  token 产出 16-32×,每 token 通信降一个数量级。M 继续增大通信占比一路走低
  (85%@M≈32 → 37%@M=8192):**通信最痛的是低并发 decode,恰是本论文主战场**。
- **Q:并发是不是"流水线轮流伺候 4 条请求"?**
  A:decode 阶段是**拼批**(4 条同 batch 一步算,M=4),不是轮流;只有 prefill 受 token
  预算约束逐条/逐块进。cache 只存 **K/V 不存 Q**(Q 现算现扔);continuous batching
  来去自由,4 是在飞上限不是凑桌条件;"变快"的本质是 161 次 AR/launch/协议等
  **固定成本被摊薄**,单个 kernel 并没变快。
- **Q:M=8192 一条对话 prefill,和 64 条请求各 128 拼成 M=8192,有区别吗?**
  A:并发不是"把 8192 切 64 份",是"M 的行由谁贡献"。**GEMM/AR 完全无区别**(矩阵乘对
  行的归属无感:同样 161 次 AR × ~134MB;vLLM 把多条请求扁平化拼接,只有注意力和
  KV 簿记看边界)。区别:①注意力打分对 8192²/2≈3350 万 vs 64×(128²/2)≈52 万,
  **少 64 倍(=L/l)**;②产出:1 个 TTFT vs 64 个 TTFT 同时还清,之后 decode M=1 独自
  (~8.5 tok/s)vs M=64 拼批(~64 tok/步);③KV cache 字节相同(8192×320KB≈2.6GB)。
  注意"把一条 8192 对话切成 64×128"**不是并发,是 chunked prefill**:块间因果依赖必须
  顺序算,总计算与总通信字节不变,但 AR 次数 161→10,304,每次重新付"等人齐"+协议地板
  (§3 的 k-分块等待放大);其收益在于切小块后可与别家 decode 混步(Sarathi),代价 TTFT 略晚。
  **每步 M 拼多大是调度旋钮,在飞多少独立请求才是并发数——两者解耦。**
- 演示页的并发上限 = 在飞请求数(含正在 prefill 的),超出排队。

## §13 通信侧:双机 16 卡上一次 AllReduce 是怎么走的

**拓扑**:节点内 8 卡(片间互联)+ 跨节点 2 张网卡各走 shca 400G IB(日志 34× `NET/IBext_v8`,
GDRDMA,零回退)。

**两个术语**(都写在 kernel 名里):**算法**用 Tree(树状归并,小消息比 Ring 省跳数);
**协议**用 LL(Low-Latency:消息直接内联在标志包里发,收到即用,适合小消息;大消息才用
Simple 协议先传数据再确认)。所以 kernel 名是
`ncclDevKernel_AllReduce_Tree_LL_Sum_b16`(b16=bf16)——RCCL 按 512KB 这个量级自动选了它们。

**AllReduce 的可分解性(Fux 一系方法的钥匙)**:AR ≡ **ReduceScatter(归约分发:每 rank
各拿到归约结果的 1/16 段)+ AllGather(全收集:大家凑齐整份)**。既然可拆,两半就都能
往前后 GEMM 的缝隙里塞——这是 §14 中 Flux 的立足点。

**kernel 内的两段**(呼应 §1.5):每个 rank 的 AR kernel = **自旋等对端** + **归并搬运**。
实测 @M=32(pid927):均值 ~496µs = **真等待 ~404µs + 真走线 ~92µs**(全局最小时长口径,
2026-10-10 修正);时长 p50 375µs、p90 742µs,波动主要来自等待。每次 AR 的全局到达散布
δ:p50=534µs、p90=687µs、p99=1176µs(逐事件数据见 ⑦ 号实测时间线页)。

## §14 四系统优化的到底是哪一环 + 它们的端到端实验做了什么

### 14.1 插入点:都在 §11 那条流水线上动刀

```
…→ RMSNorm → [QKV] → RoPE → Attn → [o_proj] ─AR①→ RMSNorm → [gate/up] → SiLU → [down] ─AR②→ …
                                    └────── Flux:AR 拆成 RS+AG,RS 融进 o_proj/down 输出侧,
                                           AG 融进下一 GEMM 输入侧,再按 chunk 交错
                                    └────── FlashOverlap:GEMM 不拆;重排 tile 输出顺序,算完一组
                                           tile 发一个信号;另一条流上的"计数 kernel"数够信号
                                           才放行对应那一段 NCCL 通信
              └── TokenWeave(对照):不动 GEMM——把 AR① 与紧随的 RMSNorm 融合成一个 kernel,
                  用 NVSHARP/Multimem 硬件多播,只占 2-8 个 SM
整体层面:triton-distributed(TileLink)= 把 Flux 式融合写成 Triton 通信原语由编译器生成;
          Syncopate = 在其上再包一层,你只写本地单 kernel,它自动完成 chunk 切分+通信计划+调度
```

### 14.2 各家端到端/基准实验(数字均于 2026-10-10 从官方仓库核实)

**Flux**(bytedance/flux,arXiv 2406.06858;MoE 版 Comet,arXiv 2502.19811,MLSys'25 AE)
- 硬件/负载:L20×8(TP8,PCIe 互联)与 H800×8(NVLink);dense MLP 与 MoE 的 kernel 级基准,
  M=4096(dense)/ 8192(MoE);训练与推理都用。
- 头条(dense,TP8,M=4096,torch+NCCL 基线 → Flux):AG+GEMM **16.95→5.90ms**、
  GEMM+RS **17.66→5.73ms**;其中通信时间 11.2→0.59ms、12.3→0.34ms(≈95%/97% 被藏掉;
  README 自注:torch 基线"仅功能正确、未优化",更强基线见 Comet 论文)。
- 依赖:NCCL + CUTLASS 4.0 + NVSHMEM;sm80/89/90。

**FlashOverlap**(infinigence/FlashOverlap,arXiv 2504.19519,**EuroSys'26**)
- 硬件/负载:RTX 3090/4090、A800/A100(**仅 sm80/86/89**,不支持 Hopper);
  算子级 GEMM+AllReduce / GEMM+ReduceScatter(+融合 RMSNorm)正确性与速度;需先离线调参
  (wave 分组搜索);多节点脚本 2026.01 才加;**端到端示例在其 roadmap 上至今未勾选**。
- 硬限制:未实现边界处理,**要求 M、N 是 128 的整数倍**——M=32 的 decode 根本不在其定义域。
- 论文报告加速最高 1.65×(技术报告数字)。

**Triton-distributed / TileLink**(ByteDance-Seed/Triton-distributed;论文 TileLink,**MLSys'25**)
- 定位:基于开源 Triton 的分布式编译器,"用它能写出媲美 CUTLASS Distributed-GEMM 与 FLUX 的 kernel"。
- 硬件/负载:GEMM+AllReduce(H800)、AG+MoE / MoE+RS(L20/H800)、**端到端 dense 推理 demo
  (2025-07,NVIDIA 与 AMD 统一支持)**、**Seed-OSS-36B-Instruct 端到端推理 1.33×**、
  Qwen3 TP megakernel(H20/H800)。2026 年持续加码:AMD MORI 后端、**昇腾 RDMA 后端(PR#179)**、
  FlashComm 通信库。
- 运行时:NVSHMEM(nvshmem4py)做对称内存通信,**不走 NCCL**。

**Syncopate**(tie-pilot-qxw/syncopate,**OSDI'26**, pp.331-347)
- 定位:编译器——输入"本地写的单个 kernel",自动变换成 chunk-centric 细粒度重叠的分布式 kernel
  (通信计划描述符 → 信号规划 → tile 调度 → lowering)。
- 硬件/负载(artifact 自述):**H100/H800 单机 4-8 卡 NVLink/NVSwitch**;端到端测试覆盖
  AG+GEMM、GEMM+RS、AG+attention、A2A+attention(Ulysses 式)、Domino 式 MLP,逐项对照
  未融合基线做正确性+计时。
- 依赖:构建于 Triton-distributed(+TLX 分支)与 NVSHMEM 之上——**谱系上它是
  Triton-distributed 的编译器层后代**。

**TokenWeave(对照,microsoft/tokenweave,arXiv 2505.11329,MLSys'26)**
- 8×H100 DGX(NVLink);TP 推理全流程;融合 AllReduce+RMSNorm,用 NVSHARP/Multimem
  硬件多播,2-8 个 SM 完成通信+归一化;**延迟最高 1.28×、吞吐最高 1.19×**;
  若干场景"比把通信整个删掉的模型还快"。
- 摘要自认的边界:重叠技术"在 vLLM/SGLang/TensorRT-LLM 里**默认全部关闭**,
  因为每步 token 数通常很小,分解式重叠反而更差"——**业界自己承认小 M 是空白**,
  TokenWeave 的下界也只到 1024。

### 14.3 端到端实验的"公约数"(= 三盲区的实验侧证据)

把五家的实验并排看,公约数非常整齐:**① 全部 NVIDIA 硬件**(仅 triton-distributed 有 AMD/昇腾后端);
**② 负载全部在大 M / 训练域**(TokenWeave 下界 1024 仍是 prefill 量级);**③ 没有任何一家注入
或测量到达偏斜**;**④ 没有任何一家做 wait/wire 分解**(它们的评测里 AR 时长≈走线,偏斜小,
工具也不显示 kernel 内自旋)。这正是第一部分三盲区在实验方法学上的根源。

## §15 第二部分新增术语表

| 术语 | 一句话解释 |
|---|---|
| wire / 走线 | 数据真正过物理连线的时间(≈消息÷带宽+协议开销);本文=dur_min(intrinsic) |
| wait / 等待 | AR kernel 内自旋等对端到齐的时间;本文=dur−dur_min,实测占墙钟 ~45% |
| wire 侧 / wait 侧 | 通信的两条独立优化轴:搬运(可藏进计算)vs 等人(只能调度消);"X 侧收益"=沿该轴最多省的墙钟 |
| BPE / 分词器 | 把文本切成子词单元的算法;Llama-3 词表 128,256 个 token |
| embedding / 嵌入 | 查表:词表大小×hidden 的矩阵,词元 id → 语义向量 |
| 投影 / GEMM | 乘一个可学习矩阵做线性变换;GEMM=通用矩阵乘 |
| logits / softmax / 采样 | 每个词元的得分 / 指数归一化成概率 / 按概率抽下一个 token |
| 残差连接 | 把上一层输入直接加回输出,给梯度留后路 |
| RMSNorm | 只用均方根缩放的归一化,比 LayerNorm 少减均值,更快 |
| RoPE | 旋转位置编码:按位置旋转 Q/K,内积自带相对位置 |
| GQA | 分组查询注意力:KV 头少于 Q 头(70B 是 64Q/8KV),省 KV cache |
| KV cache | 每层缓存历史 K/V,decode 不必重算;70B 每 token 共 ~320KB |
| paged KV | vLLM 把 KV cache 像内存页一样分页管理,减少碎片 |
| TTFT / ITPT | 首 token 延迟 / 逐 token 间隔 |
| continuous batching | 每步动态重组 batch,请求随到随走 |
| chunked prefill | 超长 prompt 切块,与 decode 混步,防止单请求霸占一步 |
| ReduceScatter / AllGather | 归约后分发各持一段 / 各持一段凑齐整份;AR=RS+AG |
| Ring / Tree;Simple / LL | 集合通信的算法(环/树)与协议(大消息/小消息低时延) |
| SM | 流多处理器,GPU 的"核";通信 kernel 会占 SM,挤占计算 |
| NVSHMEM / 对称内存 | 各卡可直读远端同布局缓冲区的通信库;细粒度通信的地基 |
| NVSHARP / Multimem | Hopper/Blackwell 的交换机侧硬件归约/多播,SM 占用极低 |
| CUTLASS / tile / wave | NVIDIA 模板库生成 GEMM;tile=分块;wave=一轮铺满 GPU 的 tile 组 |
| megakernel | 把整层/多层融合进单个大 kernel 的做法(TokenWeave、TileLink 均有涉及) |
