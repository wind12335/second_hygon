## 一、决定定位的六篇 + 一篇已核查

| 论文 | 出处 | 一句话 | 对我们的意义 |
|---|---|---|---|
| **Lagom** | arXiv 2602.20656 (2026-02, AutoCCL 原班人马) | 实验证明激进调孤立 NCCL 参数在 compute-bound 时端到端反而慢（0.87×） | **中心假设前半句被它占了** → 引作 motivation；我们的贡献必须切割到它没有的轴 |
| **Syncopate/AutoOverlap** | OSDI'26 | chunk 抽象统一 CE/NVSHMEM/SM 三原语，自动 chunk 级重叠 | 最近的"原语级统一"工作，但目标是单平台自动生成重叠，不做跨基座选择 |

| **Theseus** | SIGCOMM'26 | 运行时热切换 collective schedule | "runtime 自适应"名分被占；我们的"自适应"必须限定为"依赖释放感知的策略选择" |
| DeFT（已核查）| arXiv 2503.16815 → FGCS | DP 训练 tensor 级调度（延迟更新+背包，16×A100，vs ByteScheduler）| **无撞车**：通信黑盒、无基座/语义选择变量、纯 NV。related work 一段即可 |

## 二、确认的研究空白（三路交叉验证）

1. **语义结构轴空白**：同一资源配比下，"put-signal 分片释放 / fcollect 串行 / collective 分片重叠"等**结构不同**的策略会发生端到端排序反转——Lagom 只有资源参数轴，FlashOverlap 只有单一机制，Mist/Helix/Tessel 把通信当黑盒。
2. **"完成语义强度 × 重叠收益"权衡曲线**：无人量化（数据到达即消费 vs 远端可见 vs 全序，各换多少流水深度/SM 占用；信号通路与数据通路分离的影响）。ISPASS'25 量化了干扰代价（计算 -18.9%~-40%，NV/AMD 形态不同）但没人变成选择依据。
3. **跨 NVIDIA+国产双基座的重叠策略选择**：HetCCL(CF'26) 做互操作（混 group）、Unified OpenSHMEM(2607.08006) 做到 API 层且明言语义不统一、J.Supercomput 只做整库二选一——"能力向量 B + 端到端选择器"无人做。
4. **DUSHMEM/国产 DCU 单边通信**：英文论文为零（B、C 双路确认）。首篇公开测量 = 护城河，同时审稿人无参照系 → 须自建测量口径。

## 三、第二篇的定位（更新版）

> **Beyond Bandwidth：完成语义/依赖释放感知的 Collective-GEMM 自适应重叠策略选择（双基座：NCCL/NVSHMEM 与 RCCL/DUSHMEM）**

叙事链条：
1. Lagom（引）证明资源参数轴上 isolated≠e2e → **但资源配比并不是唯一该选的东西**；
2. 我们证明**语义结构轴**独立存在：跨 (q, N, 基座, 原语) 的反转矩阵 + release 曲线机理（Phase 1-3 已证 RCCL 内部 C0/C2 反转；Phase B 在测跨结构/跨基座）；
3. 完成语义是可测、可建模的选择变量：release 滞后（18-23us）、credit/自 WAR 开销（d1 done 比 dc 慢的 ~1.3ms）、语义档位换重叠收益的权衡曲线；
4. 双基座能力向量 B + 选择器：同一抽象、同一测量方法，NVIDIA 与海光各自选策略，不混 group。

**风险与对策**：
- ETH+NVIDIA Demystifying 系列若做跨基座建模 → 直接撞车。对策：尽快钉死 framing、抢占 DUSHMEM 首测。
- Lagom 同属中国高校体系、审稿人池可能重叠 → related work 第一段切割（他们=资源轴，我们=语义结构轴+双基座）。
- 资源竞争轴两年内饱和（Lagom/2606.09200/ISPASS'25/Theseus）→ 自变量明确超出资源配比。
- 4 卡封顶 → 靠"基座维度"取胜，双基座即护城河（与既有判断一致）。
