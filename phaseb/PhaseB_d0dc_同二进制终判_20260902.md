## 1. 为什么 formal 轮 d 族数字作废

1. formal 轮二进制带 **DS 串行门 bug**（`if(serial)` 块为空，ds 与 d1 同操作序列）；
2. DS 修复（合并双循环）改变了 d 族 host enqueue 顺序，同机同参 d1@N2048/q8 旧二进制 21639µs vs 新 18761µs（−13.3%，本机波动 <2%）——**enqueue 顺序是流式协议的一阶性能变量**；
3. 实测（§2）：DS 修复在 N4096/q8 造成 40 个百分点的符号翻转——旧二进制的 d 族不是"略有偏差"，是**方向都可能错**。

d0 参照跨根稳定（±0.1%，见 §2 表），进一步证明摆动全在 d1 侧（修复效果），而非环境漂移。

## 3. 四个终判结论

### C1. q8 反模式有 N 边界（预注册 P7 的最终形态）

d1_vs_d0 在 q8 不再是"全列负"：N512 +40.0%、N2048 +29.5%（d1 慢，p=0.004）→
**N4096 反转为 d1 快 21.0%（p=0.004）**。每片 GEMM 列数 N/q = 64/256/512：
切片计算量增大后，协议串行化开销被计算掩盖，**边界落在 N2048–N4096 之间**。
formal 轮看到的"N4096/q8 = −19.4%（d0 赢）"是 DS bug 产物（§4）。

### C2. DS 修复本身造成 N4096/q8 的 40 点符号翻转

| | d0 (µs) | d1 (µs) | d1_vs_d0 |
| --- | ---: | ---: | ---: |
| formal（旧二进制，带 bug） | 18360 | 21929 | +19.4%（d1 慢） |
| 同二进制（修复后） | 18347 | 14487 | **−21.0%（d1 快）** |

修复对 d1 的收益随 N 增大：N512 +45.4→+40.0（几乎无变化）、N2048 +41.1→+29.5（−11.6pt）、
N4096 +19.4→−21.0（**−40.4pt 翻转**）。

### C3. q16 爆炸 + dc 全网格唯一翻车格

N2048/q16：d1 慢 +69.9%（p=0.004），且 **dc 比 d0 慢 +5.9%**——dc 在其余 9 格快 12–59%，
唯独在此格翻车。128 列小切片 × 16 个同步点，连 credit 流控都撑不住：
**q 增大有双重代价（同步点增多 × 每片计算变小），这是反模式随 q 恶化的机制版**。

### C5. P14（q16fill 补批，发射前预注册）：q16 爆炸也随 N 软化，但未反转

预注册四预测（`P14_预注册_q16边界补齐_20260902.md`，发射前锁死）判定：
- **P14a HIT**：d1_vs_d0@N4096/q16 = **+40.8%**（p=0.004，d1 慢）——反模式仍在；
- **P14b HIT**：+40.8% 落在预测区间 +35~+85 内且靠近下沿——片计算 128→256 列把惩罚从 **+69.9% 救回 +40.8%**，但 16 个同步点下 256 列不足以反转（对照：q8 时 256 列 +29.5%、512 列才反转 −21.0%）→ **同步点数抬高整条边界曲线的位置，片计算量决定斜率**；
- **P14c HIT**：dc_vs_d0 = **−19.9%**（恢复领先）——N2048/q16 的 dc 翻车确系片大小所致（128 列太小），256 列时 credit 流控立刻回血；
- **P14d MISS（仅幅度）**：d1w_vs_d1 = +3.45%（预测 |差|≤2%）——方向不变（d1w +45.7% 仍深陷反模式，无任何修复效果），该格 d1 rep 间波动 ~16%，3.45% 在噪声量级；**结构性串行化结论不受影响**。

附：d0@N4096/q16 = 18357µs ≈ d0@N4096/q8 = 18347µs（整块 fcollect 与 q 无关的微一致性 ✅）。

### C4. d1w 修复无效 → P6 终判 MISS，病理升级为"协议族结构性串行化"

全 10 格 d1w≈d1≈ds（|d1w−ds|≤3.5%，多数 ≤0.6%）；d1w_vs_d0 与 d1_vs_d0 完全同步
（q8 三格 +42.0/+28.2/−20.7）。**wait placement 不是病根**——把 consumer 等待挪到
wait_stream + 事件桥，性能纹丝不动。病理定位：**协议族结构性串行化**——
逐片 credit/槽位流控把 producer 的下一片传输绑在 consumer 上一片 GEMM 完成之后，
等待放哪条流都改变不了这个依赖结构。（release→GEMM 延迟梯子 d1 5.4µs / d0 16.2µs /
r1 10–47µs 作为语义档位数据仍有效。）
